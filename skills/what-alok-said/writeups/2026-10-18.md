# What Alok said about SQL, self-dispatch, Tera and DuckDB tools

Written 2026-10-18 from all 5,361 of his prompts to Claude and Codex (09-14 to 10-18), read by eight Opus
readers. Only words he typed count. Rules live in `skills/self-dispatch/RULES.md`, checks in
`hooks/hook_checks.sql`. Where his messages disagree, the newer wins; 10-18 is the newest. Quotes are
cleaned up where he swore. No message made a measured case for replacing DuckDB with Python or bash; his
"Python is better" lines (10-15, 10-16) were sarcasm.

## 1. What he keeps saying

Ranked by how many different days raised the theme.

1. Write readable SQL, and avoid the forms he has banned. 17 days.
2. Self-dispatch has one shape, and receipts stay beside their rows. 16 days.
3. Read command output with the reader's own options, never with text tools in the pipe. 15 days.
4. Start with views, refresh incrementally, and never round-trip through files. 15 days.
5. Treat code as data: derive lists from relations and declare the inputs once. 14 days.
6. Use the extension built for the job. 14 days.

10. Tera only fills in holes. 8 days.

## 2. The rules, by theme

### 2.1 Readable SQL and banned forms (17 days)

- The older bans still hold. No `VALUES`, `COUNT(*)`, `LIMIT 1`, `OR` chains, `WITH RECURSIVE`, scalar
  subqueries in a SELECT list, `any_value`, or comma joins and `JOIN ON true`. (09-22, 09-23)
- No regular expressions on backend data; patterns only on web pages and log lines (CLAUDE.md), and
  sql_pattern_functions blocks the regex functions. The older allowance of one bare character class lost
  (section 6).
- No `LIKE` or `ILIKE` on URLs, paths or content. Choose a reader from a file-extension mapping, and parse
  URLs with urlpattern or netquack. (09-15, 09-19) "why you need a community ext/ext/%"
- Search text by matching a declared list of terms against token lists: `list_intersect` or
  `arrays_overlap` with a threshold such as `len(terms)//2`. (09-22, 10-01, 10-08, 10-15)
- Never pick by position. That means no `string_split(x, '/')[4]`, no joins on `i + 1`, and no splitting
  a path for its parent. Use hostfs functions or the index columns. (09-15, 10-09, 10-13, 10-15) "this kind
  of opaque is not useful"
- No `replace(replace(...))`; use `translate()` (09-30). No `list_transform(range(...))`, and no `list_*`
  lambdas where `UNNEST` plus WHERE does the job (10-08, 10-16). "why does it need lambdas"
- `QUALIFY`, `first_value` and `last_value` are suspect; use `arg_max` or a key join (10-08, 10-15). Never
  `MERGE INTO`; use CTAS or `INSERT OR REPLACE ... BY NAME` (10-09).
- Anti-joins are `NOT IN`, not `NOT EXISTS` (09-22). No `coalesce((SELECT ...), 0)`, no three-deep
  parentheses (09-20, 09-21). No `printf`/`format` text (10-17).
- Quoting: use `quote_literal(col)`. Never build quotes from character codes (`chr(39)`, `chr(34)`) or use
  triple quotes; sql_char_code_quotes blocks them. (10-12, 10-14, 10-16, 10-18)
- Label union branches with a projected value (`SELECT 'claude' AS source, *`), not
  `* REPLACE (literal AS col)`. (10-09) "replace why"
- A `CASE` classification returns a descriptive label, never `true`/`false` or a value copied from the
  source. (09-30)
- Compare dates with `date_trunc` and intervals, not `year()` or `month()`. Derive "current" and "prior"
  in a view relative to `now()`. (09-22, 09-24)
- No needless casts like `::VARCHAR` on text (09-29). SELECT, FROM and WHERE get their own lines (09-24).
- Name columns with an extra word (`document_id`, not `id`); CTE names say what they hold (09-22, 10-05).
- Judge a rewrite by commas plus SELECT/FROM/WHERE/WITH keywords. The smaller count wins. (09-28, 09-29)

### 2.2 Self-dispatch and receipts (16 days)

- **The shape (10-18, newest).** Render each row's statement into a `sql` column (word arrays plus
  quote_literal, a named template, or a plain concat for few holes; RULES.md 12). Then write
  `SELECT key_cols, array_agg(selfdispatch(sql)) AS receipts ... GROUP BY ALL` and
  `CROSS JOIN UNNEST(receipts)`, so each receipt sits beside its row. Never use two parallel arrays or
  `receipts[n]`. This replaces every earlier wording. (09-22, 10-12, 10-13, 10-17, 10-18)
- Use one array and one `CROSS JOIN UNNEST` per step, and never `unnest()` in a SELECT list. Nothing joins
  back to the source afterwards. (10-12, 10-13) "you don't need 2 unnest arrs"
- Each pair of CTEs is one step. The next step's statements are built from this step's receipts. Order
  comes from that dependency, never from sleep or wait rows. (09-24, 10-17) "what is the wait for?"
- When order inside one array matters, use `WITH ORDINALITY` / `array_sort` (RULES.md 2); the older
  10-14 `array_agg(... ORDER BY ...)` message lost (section 6).
- Source rows are real rows (catalog, hostfs, a table), never `range()` or `generate_series`. (10-12)
- Post through `selfdispatch(sql)`. Never curl `/sql` from a reader, never `quackapi_post` to 9495 by
  hand, and never `quack_query` back to dev. (10-09, 10-14, 10-16)
- Never add a route for work `/sql` already does. If `/sql` is broken, fix `/sql`. (10-09, 10-12) "/sql
  can do that"
- Receipts are columns: read `receipt.status`, `receipt.error`, and the dispatched statement's own columns
  (RULES.md 5). Ladders like `->'a'->'b'->>'c'` and `from_json` structures are out. One `->>` per body
  field, once, in the CTE after the unnest, is allowed until quackapi returns typed replies (RULES.md 5, 10-18).
  "a 100 line ->>'field1'->>'field2' which is not good"
- The dispatched statement returns rows, not JSON text to be re-parsed with `from_json`, `json_each` or
  `::JSON[]`. (10-12, 10-16, 10-18) "why would you ever need a from json"
- Check every stage's receipts before using them. A timeout, an error status or an empty body is a
  failure. Failed receipts stay as rows behind a flag and never break the insert. (10-14, 10-16, 10-18)
- Nothing should error. An empty first stage makes the next unnested dispatch a no-op, which works like
  try/except. (09-23, 10-16)
- Push the filter and projection into each generated statement, so a receipt carries only what is
  needed. (10-08, 10-09)
- Inside generated statements, create views, not tables. Never pass a subquery as a table-function
  argument. (10-13, 10-14) Dispatch keeps one shape, even for one statement (RULES.md 1; section 6).
- Writes: on 10-13 he wanted the COPY inside each generated statement. On 10-16 he said a dispatched
  statement reads and returns rows, with no `CREATE OR REPLACE TABLE` inside. Newer wins: 10-16.
- A statement sent to any server other than dev carries its own `INSTALL`/`LOAD` lines. (10-01)
- Paginate with one dispatch per wave, built from the last receipts' cursor. Never loop. (09-16, 09-17)
- Use self-dispatch rather than `CROSS JOIN LATERAL read_lines_lateral`. Never feed a lateral reader a
  concatenated URL. Newer wins: on 10-12 he said lateral is fine "if it works". On 10-14 he preferred
  dispatch. (09-17, 10-08, 10-12, 10-14)
- Copy a whole schema in one dispatch from `information_schema.tables`, never table by table. (10-02,
  10-08) A binder error asking for a literal is a cue to dispatch (09-24).
- Command words go into separate arrays in the first CTE: program, arguments, flags. A pipe stage is its
  own column. (10-15, 10-17, 10-18)

### 2.3 Readers and shellfs (15 days)

- Every host command runs through a shellfs reader with its `:=` options. (09-28, 10-08, 10-11)
- Use plain `read_csv` and `read_json`, never the `_auto` variants. (09-16, 09-29)
- `read_text` over a pipe needs a stated reason. Check the reader's parameters before working around it.
  (10-10, 10-13) "didn't check the parameters"
- Read lines with `read_lines` and its parameters, never `read_text` plus a newline `string_split`. Never
  split grep output on `:`. (09-23, 09-28, 10-15)
- Nothing in the pipe except the command. No `tail`/`head` (09-29), no `timeout` wrapper (09-15), no
  `sed`/`awk`/`tr` (10-09, 10-14), and no `jq` beyond the minimum `read_json` needs (10-14, 10-17).
- No `|| true` or `; true`. The shell template takes the accepted exit codes as a parameter. (10-16,
  10-17) "this was already looked into"
- No `duckdb -c` nested inside a reader (09-25). No source that starts with a side effect like `mkdir`
  (10-16). Bound slow calls with the tool's own option, like curl `--max-time` (09-15, 09-16).
- Hard-code no `/Users/...` paths, ports or roots. Use scalarfs variables, `getenv`, or a column declared
  once. (09-25, 09-28, 10-15)
- Credentials are `CREATE SECRET` statements in setup.sql, read from env vars. Fetch a secret inside the
  dispatch and never project it. (09-30, 10-17)
- Reach Postgres, S3 and MinIO from DuckDB, never psql or boto3; build Postgres objects with
  `postgres_execute` in Postgres SQL (09-14, 09-30). Newer wins: through 09-21 he said never ATTACH; on
  10-15 he allowed `ATTACH IF NOT EXISTS` in your own client. ATTACH on dev stays banned.

### 2.4 Views first, incremental refresh, no file round trips (15 days)

- Raw files, shellfs and hostfs output are unmaterialized views. Query until right, then save. One or two
  staging tables are fine. (09-15, 09-29, 10-14)
- Store raw first and parse later, so a new parsed column is one more line. (09-24, 09-27) "Everything
  should just be stored raw"
- Never COPY a result out and read it back. Put `CREATE OR REPLACE TABLE ... AS` on the SELECT. (09-15,
  09-29, 10-15)
- Every refresh is idempotent: the file rebuilds its table with CREATE OR REPLACE TABLE ... AS SELECT, so a
  lost table comes back by rerunning the file, and a second rerun changes nothing. (09-22, 09-24) "delete the
  table and rerun the sql"
- Refresh incrementally from a watermark (`max(ts)` or the hostfs mtime) plus an anti-join, so a rerun
  only shrinks. Cap a batch with a running `SUM(file_size)`. (10-08, 10-14, 10-15)
- No tombstone rows or DELETE; rebuild with CTAS (09-17, 09-22). Appended tables have a key and take
  `INSERT OR IGNORE` / `OR REPLACE ... BY NAME` (10-08).
- Crawl in two phases: one full pass, then a few items per cron tick, in one `.sql` file. (09-15, 09-19,
  09-21, 09-22)
- Keep crons few. Anything correct as a view stays a view. A cron that runs for minutes is a defect.
  (10-08) "that's just a view"
- An expensive many-file reader like `agent.stream` is a table (10-10, 10-14). Parquet only when needed,
  hive-partitioned, never in the hot path (09-16, 10-16, 10-17).
- Views over missing files return empty and never fail boot (10-16). Only `main` and `agents` schemas
  (09-21). setup.sql `.read`s one file per concern, including `extensions.sql` (10-15, 10-16).
- Git status and diff are a view: the hostfs tree joined to duck_tails hashes. Compare versions with
  `duck_diff`, one CTE per side. Newer wins: `duck_diff` (10-16) replaces "EXCEPT ALL both ways". (10-13,
  10-16)
- If a chain of views takes about a second, add the missing table. Five seconds is a defect. (09-23,
  09-24)

### 2.5 Code as data (14 days)

- Declare everything up front in the first CTE: paths, commands, reader options, prune lists. Another
  agent should change one line. (10-15, 10-16, 10-17) "another agent changes 1 line"
- Grammar, selectors, verbs and mappings are rows, joined by key. Browser targets are one row each, with
  arrays of nouns and verbs. (09-18, 10-17)
- Hand-typed lists are as lossy as min/max. Derive them from the source rows: sites from
  `agents.ext_docs`, folders from hostfs. (09-15, 09-29, 10-08) "no enumerations is also the same"
- Take column names and types from `information_schema.columns` or `DESCRIBE`. Never list them by hand.
  (09-17, 09-21, 09-22, 09-25)
- Generate near-identical statements from rows; never write three copies. Choose the reader per source
  type with `CASE` inside one generated statement. (10-08, 10-13, 10-14)
- Build JSON payloads from typed structs and catalog rows, not `json_object` CASE ladders. (10-09)
- One base view over `read_json` with an inferred schema. Variants are WHERE filters on it, and new keys
  flow in with no edit. (09-29, 10-15, 10-16)
- Generated artifacts come from a COPY of a query (09-22). Prove a generator across the whole catalog at
  once (10-13, 10-14).

### 2.6 Use the extension built for the job (14 days)

- hostfs for files, duck_tails for git, duck_hunt for test logs, sitting_duck and parser_tools for code,
  webbed for HTML, urlpattern and netquack for URLs, scalarfs for paths. (09-16, 10-07, 10-08, 10-14)
- Get file lists from the filesystem index (`fs.files`, `fs.folders`), not an ad hoc glob or `lsr()`.
  Prune in SQL with CASE or an anti-join, never with `find -prune` flags. (10-08, 10-15, 10-16)
- Parse HTML with webbed by default. Land the whole parsed document before extracting anything. (09-15,
  10-08) "are you such a genius savant of the data"
- Read a repo with `git_tree` plus `git_read_each` in one query. Never clone. Keep two to four broad
  duck_tails views, and make one file a WHERE on them. (10-10, 10-16)
- Start from hostfs `cd()`/`pwd()`, not a hard-coded repo path (10-13). Parse dates with `try_strptime`,
  never regex plus Python (10-15, 10-16).
- From fledgling and similar, copy the query definitions into views, not their macros or MCP (10-11,
  10-13). The extension catalog is one table; look functions up there first (10-16).
- A good query uses several extensions, each replacing CTEs. (09-16) "at least 3 duckdb extensions"
- Draft schemas in DuckDB, then move the DDL to Postgres, with typed columns, keys, a tenant id and two
  dates on time-travel tables. (10-01)

### 2.7 Lose nothing (12 days)

- Keep every column. Use `SELECT * EXCLUDE (...)` plus derived columns, and narrow only in the final
  SELECT. No separate preview relation. (09-24, 09-28, 10-01, 10-08) "put 1000 cols in a CTE"
- Aggregate with `array_agg`. Keep `array_agg(ts)` and take `list_min`/`list_max` later. (10-01, 10-08)
- A count is never a stand-in for the list. Newer wins: on 10-05 he offered `len(array_agg(x))` in place
  of a count. On 10-12 he called count substitutes "laundering". Keep the list, and a length may sit beside
  it. (10-05, 10-08, 10-09, 10-12)
- Profile with `SUMMARIZE` and `DESCRIBE`, never a ladder of per-column aggregates. (09-15, 09-21, 09-29,
  10-08) "uh... SUMMARIZE"
- Derive a flag with CASE and filter in a later CTE. Unmatched rows stay behind the flag. (10-01)
- Keep NULL as NULL. `COALESCE(x, '')` belongs only in the last view, for a consumer that can't take NULL.
  (09-22, 09-23) "null is a truth"
- Aggregate once upstream (09-22). One long event stream with a kind column, grouped per session-hour
  as `array_agg` of structs (09-19, 09-21, 10-16).
- Assessment queries return the rows, traced by one record, not group-by summaries. An analysis joins
  sources. It doesn't restate what DESCRIBE says. (10-05, 10-15)

### 2.8 Views and WHERE, not macros (10 days)

- Filter a view with WHERE. Never use a macro or table function that takes a path. (10-13, 10-15) "can't
  use a where clause on the view?"
- No macros until much later; write queries out in full (09-15). A macro needs Alok's yes and a
  compendium showing it removes many lines, and never hides `array_agg(selfdispatch(sql))` (09-22, 10-16,
  10-17). A macro that duplicates an extension function is wrong (10-01).
- If a view is too heavy, restructure it so WHERE pushes down to the source. Never compensate with a
  macro or a parquet cache. (10-15, 10-16, 10-17)
- Build general raw relations that everyone queries, not one table per consumer. (10-08, 10-09, 10-12)
  "slightly useful to everyone"

### 2.9 Small context (8 days)

- Return extracted content, never a whole page or document. (09-14, 09-19)
- In exploratory queries show `len(content)` and `[left(content,100), right(content,100)]`, with a small
  random LIMIT. (10-02, 10-04) "always omit the full content"
- Preview long text as an array: `arr[:10]` and `arr[-10:]`. (10-10)
- Entry views truncate and slice by default, and keep the full column for drill-down by key. (09-24)

### 2.10 Tera (8 days)

- Tera is a constructor, not the program. No `{% if %}` logic. A `{% for %}` only for loop-shaped output
  through the bash loop fallback. (09-28, 10-15, 10-17)
- Templates only for statements with many holes, from the canonical set (RULES.md 17). Otherwise statements are
  word arrays plus quote_literal, or a plain concat with few holes (RULES.md 12). Newer wins: on 09-16 he asked for one template per protocol
  shape, and on 10-09/10-12 for rendering every dispatched body from a template. On 10-18 he limited
  templates to many-hole statements.
- Nested `tera_render` is allowed when a statement dispatches further, for example rendering an array of
  statements and sending it to another host's `:9495`. Newer wins: on 09-16 he said repeated `tera_render`
  calls mean the template is wrong. (10-18)
- Pass the row as `c::JSON`, not `row_to_json(c)`. (10-15)
- Someone without the `.tera` files must find the SQL easy to rewrite. (10-08, 10-16) "if tera don't help
  reduce complexity, we will toss"

## 4. Not yet enforced

Each of these could be caught from the parsed call. Each line gives the check to add.

Dispatch and receipts:
1. `unnest()` in a SELECT list: flag any select-list `unnest` call in a statement that uses `selfdispatch`.
2. Two UNNESTs in one step: flag a second `CROSS JOIN UNNEST` per dispatch, or a join back on the key.
3. Arrow ladders: flag two or more chained `->`/`->>` on one expression. Allow a single `->>` per field.
4. Re-parsing receipts: flag `from_json`, `json_transform` or `::JSON[]` over `receipt.body`.
5. Writes inside generated SQL: parse the `selfdispatch` argument and flag `CREATE ... TABLE` or `COPY`.
8. Subquery as a table-function argument: flag a subquery node inside a table function's arguments.
9. `quack_query` to dev itself: flag `quack_query` aimed at 9494 when the tool is a dev SQL tool.
10. Lateral reader fed a concat: flag `read_lines_lateral` whose argument contains `||` or `concat`.

SQL forms:
11. `MERGE INTO`: flag the statement kind.
12. `NOT EXISTS (SELECT ...)`: flag a correlated EXISTS subquery and suggest `NOT IN`.
13. Keyless append: flag `INSERT INTO` without `OR IGNORE` or `OR REPLACE`.
14. `* REPLACE (literal AS col)`: flag REPLACE whose expression is a constant.
15. Positional picks: flag subscripted `string_split(...)[n]` and joins on `a.i = b.i + 1`.
16. `LIKE`/`ILIKE` on paths and URLs: flag them on columns named path, url, href or filename.
17. Boolean CASE labels: flag a CASE whose THEN values are all `true`/`false`.
18. Profiling ladders: flag three or more aggregates with no GROUP BY, and point to SUMMARIZE.
19. `min`/`max` aggregates: warn and suggest `array_agg` plus `list_min`/`list_max`.
20. Lambdas: warn on `list_transform`, `list_filter` or `list_reduce` with a lambda.
21. Paired `EXCEPT ALL`: warn and suggest `duck_diff`.
22. Date parts in predicates: flag `extract`, `year()` or `month()` in WHERE or JOIN ON.
23. Hard-coded test counts: flag `count`/`len`/`sum` compared with an integer literal in a check query.
24. `UNNEST(json_keys(...))`: flag it and suggest `json_group_structure`.
25. Deep parentheses: flag a column expression nested three deep, and `coalesce((SELECT ...))`.
26. `SET preserve_insertion_order`: flag it in any SQL, not only on dev.

Readers, shell and files:
27. git through shellfs: flag a reader whose command is `git diff` or `git status`.
28. Side-effect sources: flag `read_*('mkdir ...|')` and similar.
29. Inner pipes: flag a `|` inside a command literal other than the trailing one.
30. `jq` beyond the split: flag any `jq` filter in a pipe other than `jq -c '.[]'`.
31. Lines from `read_text`: flag `string_split` with a newline over a `read_text` column.
32. Ad hoc listings: flag `ls()`/`lsr()` with a literal path outside the fs views.
33. ATTACH in generated SQL: flag ATTACH without `IF NOT EXISTS`.
34. Postgres DDL through ATTACH: flag CREATE or ALTER against an attached Postgres catalog.
35. Literal secrets: flag `CREATE SECRET` with a literal token, or outside setup.sql.
36. Other schemas: flag a CREATE target whose schema is not `main` or `agents`.
37. Unpartitioned parquet: flag `COPY ... TO '*.parquet'` without `PARTITION_BY`.
38. Lake reads without a date: flag a lake-table read with no `ds` predicate.
39. setup hygiene: flag `<html` or `{% for` in `server/*.sql`, and INSTALL outside `extensions.sql`.
40. Undocumented saved queries: flag a statement in `useful_queries.sql` with no comment line above it.
41. Undocumented table functions: warn on named parameters with no comment listing them.
42. Copy-paste statements: flag three or more statements that differ only in literals.

That is 40 rules a hook could catch, plus the 18 named at the end of section 3.

## 5. Never mechanically checkable

These rules are about how the work is done, not the shape of one call:

- Query first. Issue SELECTs, preview with `LIMIT 4` or `7`, and save the file once it's right.
- Start on a named handful of keys and widen only when those rows are right.
- Test everything before offering it. Run it and show the rows.
- Never call something impossible. "Needs a literal" and "dev is down" are fixes, not findings.
- Write down what was verified, and delete wrong advice, for Claude and Codex both.
- Pick thresholds from measured distributions or percentiles, never guessed constants.
- Answer across many files in one query, not one tool call per file.
- Fix the cause of duplicate rows instead of adding `DISTINCT`.
- Build general raw relations that everyone queries, not one table per consumer.
- To choose between dispatch variants, run the same query through each and compare the results.
- Write data-quality checks only after the queries are proven: few, simple and tied to the goal.
- Log every query from every DuckDB process, as parquet.
- In assessments, trace one record through the rows instead of summarizing.
- Writers change data in one set-based SQL statement (CREATE OR REPLACE TABLE ... AS SELECT, or INSERT OR
  REPLACE ... BY NAME), never read-modify-write in app code; no BEGIN/COMMIT by default (RULES.md 11).
- Code reaches main through a PR that passed the review queue.

That is 15 rules.
